# Receiver 1 Multiplayer — Build Spec

Nov 14, 2026 (rev. 3: pill body, gear stays with the dead, ammo/enemy multipliers)

## Scope & stack

- **Form:** BepInEx 5 (x64) plugin using Harmony patches over the game's own assembly. No game code is copied or redistributed; the plugin patches behaviour at runtime.
- **Engine:** Unity 2021.3.16 (the installed Steam build; earlier drafts said 2021.3.20f1). Build against the installed game's managed DLLs (Assembly-CSharp.dll and the UnityEngine modules). The game ships no netstandard.dll, so the plugin targets .NET Framework 4.7.2.
- **Steam:** the game already ships Steamworks.NET (lobbies, P2P, UGC). Reuse it under Receiver's own app ID; do not add a second Steam integration.
- **Levels:** deterministic from a seed. The host sends the seed; every client builds the level locally. The map is never streamed.
  - The level is a line of 20 m tiles along z, built around the camera as you move (tiles within 3 enabled, enemies within 2, tiles beyond 7 deleted). In single-player every tile draws from one shared SeededRNG stream, so a tile's contents depend on build order, which differs per player.
  - In a shared run each tile's generation coroutine draws from its own stream seeded from (run seed, tile index), so every player builds identical tiles in any order, and a deleted tile is rebuilt identically. The player's starting loadout still draws from the shared stream.
  - The host keeps tiles loaded around every player (distance to the nearest player instead of to the camera), so it can run the enemies near each of them. Clients load around themselves as usual.
  - **Moving parts on a timer (0.6.2):**
    - **The problem:** add-on tiles can animate things on a cycle of their own. Multi-Floor Hotel has 4 elevators and 24 floor indicators (Animators, one 81.5 s cycle). The game starts each one whenever its tile appears, and again whenever the tile is re-enabled, so each player's elevators were out of step and a teammate riding one looked like they were floating or inside a wall.
    - **The shared clock:** in a session there is one run clock, the game time (slowed by slow motion) since the host's level began. The host sends it every second (unreliable); a client adds half its round trip (measured from its pings) and keeps a smoothed offset, snapping when it's 0.25 s out.
    - **Aligning:** every repeating Animator in a level tile (not enemies, not projectiles) is set to that clock whenever it's enabled, and again if it drifts 0.25 s. For each controller, one cycle is played once in 1/60 s steps to record its state and progress at every moment. A cycle ends when the first state starts again, which blends make longer than the clips (the hotel's 41.2 s of clips took 81.5 s). Lining up is then one jump to the right state and time. Animators that don't repeat are left to the game.
    - **Tested** (two copies, the hotel as the only tile set, 70 s): elevator heights matched within 2 cm on average, at worst 8 cm, also after one copy unloaded and reloaded an elevator's tile. Summing the clip lengths and stepping in half seconds had left a reloaded elevator 0.45 s behind.
  - **Prop groups (0.6.2):** the game's `PropGroupRandomizer` picks a tile's prop group with an unseeded random. In a session that pick is seeded from the run and the group's position. No installed tile uses it (base game or add-ons), so this only guards tiles added later.
- **Authority:** host-authoritative world (drones, pickups, damage, level); per-entity authority for each player, who owns their own body and the gun in their hands.

## Networking & transport

- **Transport abstraction:** one interface (reliable + unreliable channels, peer ids) with two implementations behind it, so game logic never knows which is active. A host can run both at once.
  - **Steam transport** — a Steam lobby plus the game's Steamworks.NET 13 P2P (`ISteamNetworking`, relay fallback allowed), for invites and friends-list joins. The game's Steamworks build has no `ISteamNetworkingSockets`. Unreliable packets go as plain `k_EP2PSendUnreliable` (0.6.1). The `NoDelay` variant used before throws packets away while Steam is still setting up or adjusting a connection (a relay route change mid-session), while reliable ones wait it out, so poses could stop for seconds.
  - **Direct IP transport** — LiteNetLib 1.3.1 (MIT; the last release with a `net471` build, needed because the game ships no netstandard.dll) for LAN, Radmin, Tailscale, Hamachi and port forwarding. Pulled forward into step 2 so two copies can be tested on one PC over 127.0.0.1. Default port 27777.
    - **Receiver's Mono has no System.Runtime.Serialization** (measured: only System, System.Core, System.Configuration, System.Numerics, System.Security and System.Xml ship). LiteNetLib's only use of it is `IgnoreDataMemberAttribute` in its reflection serializer, which every `NetManager` reached through the `NatPunchModule` it builds in its constructor (the module registers its packets with that serializer). So until 0.5.3 creating any NetManager failed and Direct IP hosting, joining and LAN search never worked. NAT punch-through is never turned on here, and NetManager only uses the module when `NatPunchEnabled` is set, so the module's constructor is skipped.
- **Star topology:** clients talk only to the host, never to each other; the host relays what others need.
- **Player caps:** a Steam lobby is capped at 250 members by Steam itself. Direct IP takes at most 16 connections, 4 from any one address (0.7.0; before that it had no limit, and thousands of connections from one machine could swell the lobby snapshot past what clients accept). Keep per-player traffic small so large groups stay practical: lobby snapshots are sent only on change and at most 10 per second.
- **Host is session authority.** Clients send input and their own owned-entity state; the host resolves world state (drone AI, damage, pickups, respawns) and broadcasts it.
- **Channels:** reliable-ordered for events (spawns, pickups, deaths, mag insert/eject, mod list, lobby state); unreliable-sequenced for high-rate transforms (body, camera, held-gun pose).
- **Join gate on connect:** protocol version and mod-list hash are exchanged in the handshake; a mismatch rejects before spawn (see Add-on sharing & join gating).
- **Same release only (0.7.0, protocol 19):** players connect only to the very same release. `Protocol.Build` ("19/0.7.0") is compared everywhere a connection starts: the Steam lobby's data and the Join list filter, the Direct IP connection request, the LAN search probe and reply, and the Hello. A mismatch says which release the host runs and to run the updater.

## Online safety

- **Nothing executable crosses the network.** Messages are fixed binary layouts read field by field; no type-driven or reflection serializers (no BinaryFormatter, no LiteNetLib NetSerializer). Add-on sharing (step 9) only ever passes Workshop item IDs to Steam.
- **Every inbound field is bounded:** sizes (reliable ≤ 256 KB, unreliable ≤ 1200 B), string byte lengths, list counts and value ranges are checked; trailing bytes, bad UTF-8 or out-of-range values drop the sender.
- **Host authority:** before the handshake only Hello is accepted (10 s timeout). After it, a client can only set its own ready flag and gun pick and answer pings. Picks are validated against the host's gun list.
- **Only structure is a protocol error:** malformed messages (wrong sizes, counts over limits, unknown kinds) disconnect the sender; odd but well-formed game values (an item momentarily far from its gun, a far position) are clamped or ignored, never a kick. Senders clamp their own positions so a dead body falling forever can't trip the host's range check.
  - **Values, everywhere (0.6.3):** until 0.6.3 the readers themselves threw on a position beyond ±100 km, a speed over 2000 m/s, a NaN or infinite number, an item spinning over 200 rad/s, or a hit's damage outside 0–20, and each of those ended the session. The host checks what clients send, but it never checked what it sent itself, so data from the host's own game, such as an enemy fallen off the level or the host's dead body falling, could throw a guest out ("The host sent invalid data"). In a real session that happened when a player was revived.
  - **Clamped now, on both ends:** every writer makes its values valid (a broken number becomes 0, positions are kept within ±99 km, speeds within 1980 m/s). Every reader clamps what still arrives and notes it once in the log ("Sync: a position arrived broken or beyond ±100 km; it was clamped instead of ending the session"). Only malformed messages disconnect.
  - **Tested:** the host sent a guest an item with a NaN coordinate, a position 500 km out and a speed of 10,000 km/s. The guest stayed connected and logged both notes.
- **World messages (in a run only):** a client can send only its own pose, gear, shots, deaths, tape pickups, item pickups and drops, and hits on enemies. Dropped-item ids carry the sender's player id, so nobody can spoof another player's items. Positions must be finite and within ±100 km, bullet speeds ≤ 2000 m/s, at most 32 pellets; a shot must start within 6 m of the shooter's body and a hit within 4 m of the enemy part, or it is ignored. Every world message carries the run id, so stragglers from an earlier run are dropped.
- **Rate limits:** per-peer token bucket (120 messages/s, burst 240); sustained flooding disconnects the peer. Peers silent for 30 s are dropped.
  - **Topped up before reading (0.6.1):** the allowance is refilled before each frame's packets are read, and grows with the frame's length, so after a long frame (a level loading, a hitch) everything a player sent meanwhile is read. It used to be refilled after reading, so a stall of a few seconds threw away that player's messages, reliable ones included: a lost "I picked this up" left the item for others to take as well.
  - **Violations fade** one a second, so only a sustained flood disconnects, never occasional bursts adding up over a long session. Ignored messages are logged ("Ignored N message(s) from …"), at most every 10 s.
  - **Per-event budgets (0.7.0):** on top of the overall limit, each costly world event has its own allowance per player (shots, projectiles and their resting places 25/s, enemy hits 40/s, item drops and pickups 20/s, sounds 30/s, cheats and tape pickups 2/s, deaths and wins 1/s, each with a burst). Every one of these makes the host build objects and relay them to everyone, so a flood under the overall limit could still stall every game; beyond its budget an event is ignored. Far above anything real play produces.
  - **Only from where the sender is (0.7.0):** shots, projectiles, item drops and tape pickups are taken only once the host knows where that player is, and only near them. A repeated item id is ignored, items waiting for their tile are kept by id (at most 2048), and the level is looked up once per batch rather than once per item.
  - **The host's level follows each player a tile at a time (0.7.0):** a player reporting far-flung positions every tick used to make the host build seven tiles around each one. Now the tile the host builds around moves one tile per 0.25 s toward the player (faster than anyone runs); a first sighting and a new level are taken as they are.
  - **A failing handler skips one message (0.7.0):** an exception from game code while handling a well-formed message is logged once per message type and skips that message; it used to abort the rest of that frame's reading. A client whose messages keep failing is still dropped.
- **What a host can make a client keep is capped (0.7.0):** skins for at most 64 players, enemy states for at most 50,000 enemies not loaded here, at most 256 Green Demons.
- **Who can connect:**
  - Steam: P2P sessions are accepted only from current lobby members. A **Friends only** lobby (the default) also requires being the host's Steam friend; **Public** lobbies appear in everyone's Join list; **Invite only** lobbies are hidden. Clients accept packets only from the lobby owner.
  - Direct IP: off until the host turns it on. Connection requests must carry the mod key, the exact protocol version and release, and the optional password (compared in constant time); anything else is refused before a peer exists. After 5 wrong passwords an address is refused for the rest of the session. The password is not encrypted on the way (Direct IP traffic isn't). LAN discovery answers only an exact probe, with a small fixed reply, and only from this computer's own networks (private ranges, or the subnet of one of its adapters, which covers Radmin and Hamachi), so a forwarded port tells the internet nothing.
  - The host can **Kick** any player; kicked Steam IDs and IP addresses are refused for the rest of the session.
- **Names are display-only:** Steam players are shown with the name Steam reports to the host (not what the client claims). All names have control characters and rich-text markup stripped and are capped at 24 characters.
- **Privacy:** Steam lobby data holds only the protocol version, the host's display name and the lobby state; no IPs or Steam IDs are broadcast in lobby state. The host's own addresses are shown only on the host's screen when Direct IP is on. Like most P2P games, Steam P2P may connect host and client directly, so each can learn the other's IP; clients never connect to each other.

## Menu & session flow

- The pause menu (the game's only menu) gains one **Multiplayer** button, cloned from the existing buttons so it matches their style, placed to the right of Resume so the hand-placed button staircase is untouched.
- Multiplayer screen offers **Host Game** and **Join Game**.
  - **Host** opens the waiting room (below); the host picks the seed (new or current).
  - **Joining a run under way (0.6.3, protocol 18):** a player who joins after the round has started loads the level at its start, then starts inside a teammate who's alive, placed the way a revive places you, with the screen black until they're in. It waits up to 10 s for a living teammate's position and up to 10 s for the floor there to be built, and puts the body back if it drops within a second. With nobody alive, they stay at the start.
  - **No leaving to respawn:** the host remembers who left this run (Steam ID, or address and name over Direct IP) and whether they were down. A player who was down rejoins down, spectating, and counts toward a team wipe until a tape is found. A tape found while they're away brings them back too, so they rejoin alive. A new run forgets all of it.
  - **Tested** (two copies, headless, three passes): a player who left alive rejoined inside the host, after the host had moved two tiles from the start; one who left down rejoined down, with no wipe, and the next tape revived them; one who left down while a tape was found rejoined alive inside the host. In one earlier pass a rejoiner landed near the start instead; it didn't happen again in three more passes, with logging that would have shown its cause.
  - **Join** shows a server list (Steam lobbies the mod publishes, plus LAN broadcast discovery) and a **Direct Connect** field (IP:port) that works over LAN/Radmin/Tailscale.
- **Steam invites:** friends-list invite and “Join Game” resolve to the host's lobby and connect through the Steam transport.
- **Session start:** the round starts from the waiting room. One life each; the normal loop otherwise, with no reset when someone joins.
- **Scene loading takes everyone:** the pause menu's own Scene Loading buttons open `scene` ("Load Apartments", the main level) and `range` ("Load Gun Range"). In a session the host's click on either starts a fresh shared run in that scene for everyone (from the waiting room too), and the host's Restart restarts the scene everyone is in (a new level for the main one). A team wipe restarts the same scene. During a run a client's scene buttons and Restart only show a notice; in the waiting room a client can still load a scene for themselves until the host starts. Only the main level and scenes the game's menu offers are ever loaded on the host's word, and only if the client's game has them (otherwise it leaves with a message).
- **The gun range in a session:** everyone spawns there with their run gun; players, shots, gear, sounds, ammo piles, pickups and drops are shared. Its five targets aren't part of the main level's tiles, so they stay local to each player.

## Waiting room & loadout

- **Ready list:** hosting opens a waiting room listing every connected player by Steam persona name (or a chosen name on Direct IP). Each player toggles **Ready / Unready** for themselves; the list shows everyone's state live. Names appear only here, never in the round.
- **Countdown:** when every player in the room is ready, a 3-second countdown (3, 2, 1) runs and the round starts. Any player unreadying, or a new player joining, cancels the countdown.
- **Start Game:** the host has a **Start Game** button that starts the match immediately regardless of ready state; unready players spawn with everyone else.
- **Match start:** whether from Start Game or the countdown, every player's screen fades to black, a fresh match loads (the game scene reloaded with the run seed and each player's gun), and the screen fades back in once that player has spawned. Every start is a new match, even if players were mid-run.
- **Late joiners** during a run go straight into the current run (same seed) at the start spawn.
- **New Run (host, during a run):** returns everyone to the waiting room with ready flags cleared; the waiting room opens on every client.
- **Connections (host):** Steam lobby visibility (Friends only by default, Public, Invite only), **Invite Steam friends** (Steam overlay), and an opt-in **Direct IP** listener with port and optional password. When Direct IP is on, the host's own LAN/VPN addresses are shown to the host so they can share one.
- **During a session the game never pauses or stops:** the game pauses whenever its menu opens, and players host or join from that menu, so time is kept running every frame while a session exists. Unity also stops the whole game when its window loses focus (alt-tab), which silenced the network and timed everyone out; during a session the game runs in the background. Peers are dropped only after 30 s of silence. The local restart key and the menu's restart/scene buttons are disabled during a run (only the host changes the level).
- **Weapon choice (host toggle):** a host setting, **Allow weapon choice**, on or off.
  - **Off:** everyone's starting gun is randomized exactly as in single-player.
  - **On:** each player has a dropdown next to their own name in the ready list listing every gun currently loaded (base game plus enabled add-on guns, identical on all clients because of the join gate). **Default** is the first entry and keeps the normal randomized pick.
  - Picks are sent to the host, which validates the choice against its own gun list and includes the final per-player loadout in the start message. A random **Default** pick is rolled by the host so every client agrees on it.
- **Friendly fire (host toggle):** off by default, and can be changed during a run (Multiplayer button). Off: a teammate's bullet still hits you like in the base game (puff, sound, the bullet hole on your screen) but does no damage. On: it hurts you exactly like a turret's. Sent with the settings and shown read-only to joiners.
- **No ammo or enemy multipliers:** the base game has none (its only gameplay settings are the Modifiers below), so the mod adds none. (Sliders for them existed in earlier test builds without ever being connected; removed in 0.5.3.)
- **The game's Modifiers are the host's:** the pause menu's Modifiers window (Green Demon, Thick Fog, Spawn magazines, Tough Killdrones, Deadly Threat) and the tape limit. The game clears these at every launch. In a session everyone uses the host's values: sent on joining, with every run, and the moment the host ticks or unticks one (Thick Fog switches on everyone's screen at once; the others take effect when a level loads, as in single-player). A client's checkboxes show the host's values, and ticking one only shows a note; their own values come back when the session ends.
- **Lobby state is host-owned:** ready flags, picks, the weapon-choice and friendly-fire toggles and the countdown are host state broadcast on the reliable channel; clients only send requests to change their own entry.

## State synchronization (the core)

The hardest and most important part. Build and prove it first.

- **Per-entity authority:** each player owns and broadcasts their own body transform, camera orientation, and the state of the gun/items in their hands. The host owns drones, world props, pickups, and damage resolution.
- **Player presence — the pill:** each remote player is a plain capsule, and the game already has one. Measured on the spawned `Player` object (tag `Player`, layer 9 `Character`):
  - `CharacterController` for movement: height 0.8, radius 0.2, centre at the origin.
  - `CapsuleCollider` hitbox on the same object: height 1.3, radius 0.2, centre +0.25 (feet to 1.3 m), plus a kinematic Rigidbody.
  - Child `Capsule`: Unity's built-in capsule mesh, about 0.43 m wide × 1.34 m tall, renderer on, shadows off. It matches the hitbox. Its own collider is disabled.
  - Child `Graphics`: an unused body mesh with its renderer disabled.
  - The eye sits 1.1 m above the feet, inside the capsule, which is why players never see it (backface culling).
  - A remote pill is a copy of that `Capsule` object (same mesh, material and scale) with the hitbox capsule. It follows crouching the way the game does it: the whole player object's height scale goes from 1.0 down to 0.5.
  - **Hidden from its owner:** the local `Capsule` renderer is disabled rather than relying on the camera being inside it, so death-camera moves and spectating can't reveal it. While spectating a player in first person, that player's pill is hidden too.
  - **See-through, more so up close:** the game's pill material (`Translucent`) is the Standard shader in premultiplied-transparent mode with alpha 0, so only its faint 0.125 grey glow and its gloss show; that is why teammates are see-through. Each remote pill draws its own copy of it (the game's material is never changed) whose glow scales with how close the camera is: full from 6 m out, easing down to 15% at arm's length (0.6 m), and nothing at all only with the camera inside the body (within the capsule's radius of its axis, ramping over the last 0.2 m).
  - **No names:** no floating names or labels over players, and no inventory shown to others.
  - Body transform, crouch scale and camera look go on the unreliable channel every 20 Hz tick (~0.5 KB/s per player; skipping unchanged ticks left gaps that made spectating stutter); the host relays everyone's poses in batches. Receivers render 150 ms behind with interpolation (room for jitter on the two-hop path) and keep moving for up to 100 ms when a packet is late.
  - **Silence doesn't hide a player (0.6.1):** if a player's movement data stops, they're drawn where they were last seen for up to 20 s (it was 3 s, so a few seconds of lost packets made them vanish); they still leave at the 30 s connection timeout. A 2 s silence is logged ("No movement data from … for 2 s"), and again when data resumes, with how long it lasted. The per-minute sync stats count gaps over 1 s.
  - The remote pill sits on the player's layer (9) with a kinematic Rigidbody, so bullets stop on it and holes stick to it, and turrets (which check line of sight against layer 0 only) can see it. Players pass through each other (collisions with the local player are ignored), so nobody gets stuck at the shared spawn.
- **Shots (replayed, visual):** the shooter captures each discharge (muzzle-flash pose and every pellet's start and velocity) and sends it; the host relays it. Capture notes the bullets that exist before `FiringSystem.Discharge` and reads the new ones afterwards: `BulletScript.SetVelocity` is 9 bytes and the Mono JIT inlines it into the firing code, so a hook on it never fires (methods under ~20 bytes of IL can't be patched this way). Ricochets spawned by a replayed bullet are found the same way and marked as replays. Everyone else replays it with the gun's own bullet prefab, muzzle flash and gunshot sound, so bullets, ricochets, holes, sparks and broken lights appear for everyone. Replayed bullets never damage enemies. The game draws a trail at 5% opacity, plain to the shooter looking down it but nearly invisible from the side, so replayed player trails are drawn 4× brighter.
- **Projectiles (0.6.2, protocol 17):** some add-on guns fire a physics object instead of a bullet: the game's `ProjectileScript` with a Rigidbody, launched by `FiringSystem.Discharge` at the muzzle with `AddForce(forward × exit_velocity, Impulse)`. Before 0.6.2 nobody else saw them. Of the 21 installed add-on guns that's three; the other 18 and the base game's guns fire bullets:
  - **GG 9000:** a 10 kg glue blob. On a hit it turns kinematic, plays its grow animation and switches on a solid collider, so it can be climbed.
  - **Nerf Maverick:** a suction dart that sticks.
  - **TP Gun:** a cloth that never sticks.
  - **On a hit, the game:** sticks the projectile (with `attach_on_hit`) to the local player's view, to an enemy, or else to the tile's decals, then runs its `on_collision` actions.
  - **Replay:** the shooter's capture also notes new `ProjectileScript`s and sends their ids (shooter and counter, like dropped items) and poses in their own message. Everyone else spawns the same prefab there with the same impulse, ignoring collisions with the shooter's pill. The host checks the shot starts at the shooter's body and each projectile within 2 m of the muzzle.
  - **Where it came to rest:** when the shooter's own projectile sticks, it reports where: on the level (world pose), on an enemy (its id and pose on it), or on a teammate (their id and pose on their body). One that never sticks reports where it is once it sleeps, or after 8 s. Every copy is moved exactly there, still flying ones are frozen, and the projectile's own `on_collision` actions are run, so the glue blob is solid and climbable for everyone. One that stuck to you stays on your view, as the game does.
  - **Kept for the run:** resting places are kept, up to 2048 per run. A projectile lost with its tile, or one a late joiner never saw (the host sends them on join), is rebuilt in place once its tile, or its enemy, is there.
  - **Damage:** a hit is handled through the same checks as bullets. Only the shooter's own copy damages enemies (a client reports the hit to the host), and a replayed projectile hurts players only with friendly fire. Before, a client's projectile hits on enemies were lost.
  - **Tested** (two copies, the game's own `DISCHARGE` request): the host fired two GG 9000 blobs and the guest two darts, and every copy came to rest at the same spot, to 0.1 mm. The blobs were solid on both, a blob the guest lost was rebuilt in place within 2 s, and the TP Gun's cloth settled at the same spot.
  - **Not tested:** hits on enemies and players, sticking to an enemy or a teammate, late joiners, and Steam.
- **What else was checked (0.6.2):** every installed add-on and base-game tile was loaded and inspected. There are no walk-in triggers (`TriggerScript`, which fires only for the local player), no shootable triggers, no prop randomizers and no physics props. The only loose physics objects are items, casings and projectiles, all shared. The only timed motion is the hotel's elevators (above). Tiles added later that use those scripts could still differ.
- **Damage authority:**
  - **Enemies:** the shooter's own bullet decides the hit. A client reports it to the host (enemy id, part, hit point, velocity, damage); the host checks the part is within 4 m of the reported point, applies it through the game's own `WasShot`, and broadcasts the destroyed part. Clients' enemies only take damage the host reports. A bullet passing into an internal part goes through `WasShotInternal`, which is inlined too, so that case is caught in `Damage` (replayed bullets never damage; a client's own bullet is reported).
  - **Players:** the victim's machine decides, from the replayed bullet that reaches them. Turret bullets always can hurt; another player's bullet only with **Friendly fire** on (host toggle, off by default; with it off, those bullets pass through you). A drone's shock is decided on the host and sent to the player it reaches.
- **Visible effects (later):** other players' flashlights and ejected casings. Keep the “bullet hits your screen” effect local — only the victim's client plays it.
- **Enemies (host-authoritative):** every machine builds the same turrets and drones per tile; an enemy's id is its tile index plus spawn order. The host runs the AI against the nearest living player (local or remote) and streams pose, turret aim, drone camera, rotor speed, alert light, AI state and which parts are alive (20 Hz, changed only, 1 s keyframe). Clients turn theirs into puppets (AI and physics off) and replay alert sounds, shock-prod sparks, rotor spin, lens flares and the motor hum (the AI update normally drives it: sleeps beyond the sleep distance, drone volume from rotor speed and distance and muffled out of sight, turret pitch from swing speed). Turret shots are sent as events and replayed as hostile bullets. Damage on an enemy whose tile was deleted is remembered and reapplied when the tile is rebuilt.
- **Stability:** interpolate remote transforms; keep owner-side authority on gun handling to avoid rubber-banding; run a fixed network tick independent of framerate.
- **Gear on the body (the belt):** each player streams what they carry (20 Hz when it changes, 1 s heartbeat; the host relays it). Others draw display-only copies of the game's own prefabs (scripts, colliders and sounds stripped) on the pill:
  - the belt itself is invisible; only what hangs on it shows;
  - holstered gun on the right hip, pointing straight down;
  - magazines and the flashlight down the left side, front to back by inventory slot (other guns' carried magazines after them);
  - loose rounds packed across the back (14 per row, up to 42 shown);
  - a drawn gun, magazine in hand or held flashlight floating exactly where the player holds them (pose relative to their eyes), like in normal play;
  - items glide (0.3 s) between belt and hand when drawn or put away.
- **Smooth held items:** every gear message carries the owner's tick (the same clock as their pose), each held item and gun part keeps a short history, and viewers draw them at the same render moment as the owner's pose (150 ms behind), interpolating pose and parts. A held gun moves as smoothly as the camera, including through a spectator's eyes.
- **Handling sounds:** every gun, magazine and body sound the game plays (slide, hammer, safety, cylinder, magazine in and out, loading rounds, holstering, footsteps...) goes through three small methods that pick a random clip from a group and play it; they're replaced with identical code that also reports which clip played, and everyone else plays that clip at the player's hands (body sounds at their body) with a short-range rolloff. Gunshots are left to the shot replay. Magazines lying in the world aren't reported (their bounces play on every machine anyway).
- **Live gun handling:** gun parts are animated by the game as plain child transforms (slide, hammer, trigger, safety, cylinder, yoke, extractor rod, bolt). Every part not at its rest pose is mirrored by index into the prefab's hierarchy; the inserted magazine (with its visible rounds), the chambered round and revolver rounds are mirrored as attachments. Works for every gun, including add-on guns.
- **Flashlights:** a held flashlight's point and spot light intensities are mirrored, so everyone sees its beam.
- **Shell casings and ejected rounds:** see Synced world items.

## Skins

- **Where:** a Skin section in the Multiplayer screen and in the waiting room: a slowly turning, see-through preview of your pill, **Apply skin…**, **Remove skin**, a **Player skins: Enabled / Disabled** switch (whether other players' skins show), and a status line.
- **Choosing:** Apply opens the Windows file picker (on its own thread, so the game and network keep running) for an image from your own folders. The image is scaled to 256×256 and saved as a JPEG (a few tens of KB) in the plugin's config folder, so it's still applied next launch. Remove deletes it.
  - **Any image Windows can read (0.6.3):** the game's decoder reads only PNG and JPG, and it goes by the file's contents. So a WebP renamed to .png (what many "converters" do) was refused as "not a PNG or JPG". Whatever the game can't read now goes to the Windows Imaging Component (the decoder File Explorer uses, called through its COM interfaces), which scales it to 256×256. That covers WebP, BMP, GIF, TIFF, and HEIC or AVIF where Windows has those codecs. The picker lists those types plus All files. If Windows can't read it either, the status says so, and for WebP names Microsoft's free WebP Image Extensions.
  - **Tested:** normal and 16-bit PNG through the game's decoder; BMP, GIF, TIFF, lossless and lossy WebP, and a WebP renamed to .png through Windows, all with the right colours; a corrupt file is refused with a message.
- **Preview:** the same capsule mesh as the player's pill, translucent, with your image wrapped on it, drawn on a hidden stage (layer 31, never seen by the game's camera) by its own light and camera into the menu, only while a preview is on screen; fog is switched off for that camera.
- **Others see it:** your skin goes to the host when you join and whenever you change it; the host keeps every player's skin, passes it on, and gives a joining player all of them. Other players' pills show your image as their texture (also during the death fade-out).
- **Still see-through:** a skinned pill keeps the game's pill material and adds the image at 55% opacity, plus a faint glow in the image's own colours (emission map, 0.18) so it still reads in dark rooms. Both scale with the same closeness as the plain pill, so a skin is a faint ghost at arm's length and gone only from inside the body. A dead skinned player fades out from there over 1.5 s on the same material.
- **Safety:** skins are images only: PNG or JPEG, at most 128 KB and 512×512, checked from the file header before anything decodes them; a picked file may be at most 8192 pixels a side (0.7.0: checked from its header before decoding, so a small file claiming a huge picture can't use up the memory); a player can change skin at most every 3 s; **Player skins: Disabled** (config `ShowOtherSkins`) shows everyone as the plain pill.

## Death, bodies & camera

The game is first-person with no player body and a scripted death (the head falls, the screen fades to black over ~3.3 s, then the level reloads). In a session the level never reloads on its own.

- **One life:** a dead player stays dead; the client reports the death to the host, which keeps the list of who is dead and broadcasts it. When a run starts, the previous level's player object (often dead) still exists until the new scene loads; it is forgotten at once so it can't be reported as a death in the new run.
- **Fade-out:** others see the dead player's pill fade out over 1.5 s where they fell (built-in transparent shader; shrink fallback), and their belt and held items disappear. Bullets pass through and enemies ignore them.
- **The dying player's own view:** the game's death (head fall, black fade) plays as normal.
- **Fades:** every change of view fades out and back in (eased): death → spectate (fade to black over the end of the death from 2.6 s, switch, fade in over 1 s), switching teammates (quick out and in), and revive (fade out of the spectator view, revive and teleport, fade in on your own eyes). A newer fade supersedes an older one, and a revive takes precedence over a spectate change in flight.
- **Spectate:** the view fades in on a living teammate's eyes, mirroring their view: their camera position and look, their held gun and its live handling, their inventory along the bottom of the screen and their loose rounds top-left, placed as the game places the player's own. Their name shows top-right (the one place names appear in a run). Click to switch teammates. The dead player's own items are hidden and their flashlight kept dark every frame (the game's FlashlightScript re-enables its lights each frame), bullet holes the game stuck on their camera ("in your screen") are wiped and any new ones cleared, the death blackout and audio mute are suppressed, and the level streams around whoever is watched. Camera and camera-relative items are placed at the end of the frame so they don't jitter.
- **Loading, as they see it (0.5.5):** round counts (their counter and a held magazine) change at the render time, with the hands (they used to change when the packet arrived, ~150 ms early), and anything that appears in their hands (a round in a revolver chamber) appears then too. When a round goes into the magazine in their hand, the copy replays the game's own load (`mag_script`: the stack shifts down while the new top round moves from `point_start_load` to `point_load`, then settles into its slot; each stage `bulletReloadTime`). Spectating, the round that leaves their counter flies down (0.14 s, growing to full size) to where it goes in: the magazine's `point_start_load`, a revolver chamber's new round, or for a gun with a built-in magazine (a tube) the gun's own load point, unless they just dropped a loose round on the ground. Only on the spectator's screen; on the body the magazine still animates.
- **Gear stays with the dead player:** nothing drops on death; the inventory is untouched because the scene isn't reloaded.
- **The dead body stays put (0.6.3):** 3 s after a death, the body is held where it lies. Watching a teammate, the level around it can unload on that machine, and the body then fell forever, tens of kilometres within minutes, which fed absurd values into what that player sent. Tested by moving a dead body 60 m down: it was back in place within half a second.
- **Tapes are shared and revive:** a tape picked up by any living player is given to every player (everyone hears it, so the team progresses together), and every dead player is revived with the gear they died with (fade out, revive, teleport, fade in) inside the player who found it. The finder's message carries where their body was and its crouch height.
- **No tape is missed (0.6.1, protocol 16):**
  - **Bleeding out:** a shot player doesn't go down at once. The game sets `dying` and counts health down for up to a second (a hit has a 30% chance to kill outright). A revive that arrived in that second used to be ignored (not down yet), and the player went down for good a moment later. Now it waits, and they come back as soon as they're down. This applies only to a teammate's tape: the finder isn't saved by their own.
  - **Late death reports:** every tape sends a revive to everyone but its finder, and a death report carries how many revives that player had received this run. The host counts what it sent to each player (not the finder their own tape's, nor a late joiner the ones from before they arrived). A report with fewer than that means the player went down before the newest revive reached them, so it brings them back, and the host doesn't count them as dead. Before, such a report reached the host after the tape and it counted a living player as dead. That player's tapes were then ignored (the host stayed down), and a team wipe could restart the run while they were alive.
  - **A failed revive is reported:** if a revive doesn't bring the player back, they report their death again, so a wipe still happens.
- **Long-session test (0.6.1):** two copies on one PC over Direct IP, about 4.5 minutes and three runs, scripted. Everything below passed, on both sides:
  - **Presence:** the 16-bit send tick wrapped early in run 1, and no check of 1,863 found a living teammate missing.
  - **Gaps:** the guest went silent for 8 s and stayed drawn throughout. The host froze for 8 s; it logged that it had frozen, not that the guest went quiet, and ignored nothing afterwards.
  - **Revives:** a plain revive; a tape found while bleeding out (they came back once down); a death report held back 1.5 s past the tape (ignored, no false death).
  - **Tapes and wipes:** the guest's tape revived the downed host with no wipe. Both down gave a wipe and a new run, and the same again in run 2.
  - **Seeds and kits:** seeds matched in every run, and every run rolled a fresh start kit.
  - **Not tested:** Steam P2P (the send-mode change only applies there), real network loss, and more than two players. The first version of the revive counting compared a player's received revives with every revive sent; the finder isn't sent their own tape's revive, so their next death was ignored and the wipe never came. The test caught it, and counting now happens per player.
- **Revive placement:** players don't collide and the finder is standing somewhere open, so the revived body goes inside theirs, feet on their feet: first where the finder is now (as drawn on the reviving machine), else where they picked the tape up. It stands up if a standing body fits there; otherwise it takes the finder's crouch (crouch state and the game's height spring set to match). If the floor is in the way (a pose a few ticks old, a moving lift) it is lifted in 5 cm steps, up to 0.6 m and never up through a ceiling. The fit test is the player's own controller capsule, 3 cm slimmer, against every layer the player collides with, ignoring triggers, the player's own colliders, other players' bodies and loose physics props. Without this, a standing body placed where a crouched finder was started partly inside the floor and the game's character controller pushed it out sideways, into walls. If the level there hasn't been built yet on the reviving machine (they were watching someone else), the body is held in place behind the black screen until there's a floor under it (up to 2.5 s).
- **One death changes nothing else:** the level, enemies and items stay exactly as they are while anyone is alive.
- **Team wipe:** when everyone is dead for 4 s, the host restarts with a fresh level, like single-player (new seed unless the host fixed one).
- **Win:** the game wins when you've heard as many tapes as the run has (`total_tapes`: 11 by default, all of them with the tape limit off); each tape picked up queues for playing and plays on its own. Tapes come from ammo piles (1 in 4), which every machine rolls the same way, and picking one up removes it for everyone and gives every player a tape to hear, so the whole team hears them all. The first player to hear the last one wins it for the team: a client reports it, and the host accepts it once the team has found at least as many tapes as a run has. Everyone gets a notice ("Every tape found and heard: the team won the run!"), and 6 s later the host ends the run and the waiting room opens with that message. The solo win scene is skipped.
- **Later:** a falling-pill death (physics capsule pushed by the hit) instead of the fade.

## Weapons & cross-gun ammo

- **No drops on death:** dead players keep their gear (see Death, bodies & camera).
- **Shared ammo pool:** ammo piles stock one of the run's guns (the starting guns of everyone in the run, fixed when it starts and sent in the start message), chosen from the run seed and the pile's position. The set can't change mid-run (piles must be identical on every machine whenever each loads them), so a player who joins mid-run has their gun's ammo in piles from the next run. Each log's run check lists the run's ammo guns, and the sync stats count piles per gun. The game rolls pile contents (round count, magazine, tape, flashlight) and magazine round counts with an unseeded random; in a session those rolls are seeded from the run seed and the item's position, so every player sees identical piles.
- **Synced world items:** every pile item gets an id from its pile; picking one up removes it for everyone (also on tiles loaded later, and for late joiners). Anything that leaves a player's possession as a free physics object (dropped magazine or flashlight, ejected live round, spent casing, revolver rounds) is created for everyone with its position, velocity and spin; if its tile isn't loaded on a machine yet, it appears when the tile loads.
- **Carrying for teammates:** Pickup (G) also takes rounds and magazines made for other guns. They're carried, shown on the belt, and can't be loaded into your gun.
- **Other guns' magazines in hand:** with your hand empty, Pickup takes the nearest magazine into your off hand even if it's for another gun (the game's own pickup code, by pointing its magazine-name filter at that prefab for the call). Z loads it from the rounds you carry for that gun, R unloads into them, it stows and drops (E) as usual, and it can't be inserted into your own gun: the game starts an insert (`mag_stage = HOLD_TO_INSERT`) and finishes it by emptying the hand without checking whether `InsertMag` succeeded, so the start condition itself is guarded and the magazine just stays in your hand (a refused insert that is reached anyway drops the magazine as a normal item rather than leaving it floating). Your own loose rounds never go into it, and its rounds never into your gun. With your hand full, other guns' magazines go to your carried items instead.
- **No duplicates:** each world item is taken once per pickup scan (items have several colliders and Destroy is deferred to the end of the frame), and any tagged world item that comes into your possession by any path (pickup, grabbing an ejected magazine back) is announced as taken, so a drop-and-regrab never leaves copies.
- **Dropping:** Ctrl + mouse wheel steps through the row one item at a time, forward and back (stopping at the ends): each of your loose rounds, then other guns' rounds, then other guns' magazines. The middle mouse button drops exactly the highlighted one. The plain wheel stays the game's (it spins a revolver's cylinder); while Ctrl is held the cylinder doesn't spin. Ctrl + wheel uses the game's own loose-round display exactly as picking up a round does: it sets the same 2-second show timer (`picked_up_bullet_delay`), so the row of rounds slides in at the top left, and the chosen round gets the same spring kick (pops bigger) and stays slightly enlarged (0.39 vs 0.3) while the row shows. Other guns' rounds and magazines you carry continue that row with the game's layout and springs. Ctrl + wheel with nothing to drop still shows the row, to check your rounds. The game's own Drop (E) still drops a magazine in hand or the flashlight.
- **Modifiers come from the host:** deadly enemies, tougher enemies, green demon, spawn magazines and the tape limit are sent with the run start and applied for everyone; a client's own values are restored when the session ends.
- **Later:** gun cycling (hold holster to swap guns), and loading other guns' carried magazines into a matching gun picked up from a teammate.
- **Starting kit (base game, unchanged):** loose rounds 0–9 and 0–2 spare magazines (each 0 to full) for magazine guns. A gun without a detachable magazine (the game's `mag_object` is empty: revolvers, and add-on guns such as a tube-fed shotgun or a bolt rifle) gets 0–19 more loose rounds instead of spare magazines, so up to 28 (`AimScript.Start`: `SeededRNG.Range(10)` + `Range(20)`). A fresh level rolls a fresh kit: nothing carries over from the run before (checked against a real 11-run session's logs, 0.6.1). Rolled from the run seed, so everyone's kit matches within a run; magazine fills are seeded by position so every machine agrees. Each player's starting kit is written to the log at every run start.

## Cheats & modifiers

- **Cheats** (typed codes, the game's own): `slomo` (time at 10%), `iddqd` (god mode), `idinf` (infinite ammo), `idkfa` (loose rounds up to 30). Like single-player they switch off when a level loads.
  - **Slow motion is the team's:** time is shared (the host runs the enemies), so typing `slomo` asks the host, which toggles it for everyone; the time scale is held every frame during a run (the menu pause and the game's own toggle would change it), and it goes back to normal when the run ends. Networking runs on real time, so nothing else changes.
  - **God mode, infinite ammo and the ammo refill** are for the player who typed them, as in single-player. What they do is already shared (no deaths from turrets, drones, the Green Demon, falls or friendly fire; shots; rounds on the belt).
  - **Everyone is told** who used which cheat (a short notice at the top of the screen).
- **Green Demon, one per player:** in single-player the level puts a spawner 0.8 m in front of you when it starts (a warning light, green to orange over 8 s), then the demon (a drone, `RobotType.GREEN_DEMON`) that hunts you and kills on touch. In a session the game's own spawner is skipped and the host makes one per living player, 1.5 s after they're up, in front of them, shown to everyone. Each demon hunts only its own player (host-run AI like every enemy, a puppet with spinning rotors, shock prod and motor hum elsewhere; its shock reaches a remote player as the shock message). A player who dies loses their demon; when revived a new one starts in front of them, as a fresh level would. Late joiners get theirs and see everyone else's; a client still loading the level when one is announced makes it when the level is ready (straight away if its warning already ran out).
- **Thick Fog** is the level's fog switched on (the checkbox also calls `optionsmenuscript.SetFog`); with the host's values it's the same for everyone, live.

## Add-on sharing & join gating

**Built (0.5.0, reworked in 0.5.2):**
- **How the game loads add-ons (measured):** three kinds, guns, tapes and level tiles (`ModType` 0/1/2). Local `modfile_*` folders are imported at launch only with mods on; Steam Workshop items are imported whether or not mods are on: at launch the game asks Steam for the subscribed items (first 50, sorted by title) and imports each installed one in the background, and again whenever Steam finishes installing an item. A level uses them only with mods on (`mods_enabled`), and `mod_gun_loading` / `mod_tape_loading` / `mod_tile_loading` decide per kind whether add-ons join the base game's (0, and 3 in practice), replace it (1) or are left out (2). The game doesn't wait for the imports before building the first level: with 11 Workshop guns they finished about 2 s after it.
- **Wait for add-ons:** hosting and joining first wait (up to a minute, with a status line) until Steam has answered and nothing is still importing, so the lists compared are complete.
- **The host's mod settings apply to everyone:** `mods_enabled` and the three loading settings travel with the gameplay modifiers, in the welcome and with every run, and a client's own values are put back when the session ends. So a level is built from the same guns, tapes and tiles everywhere, whatever each player's own settings.
  - **Crash-safe (0.7.0):** the client's own values are also saved in its settings while a session uses the host's; if the game closes mid-session, they're put back at the next launch. The host's values are used exactly as sent, not clamped: the game reads them loosely (a loading setting is "left out" at 2, "replace" at 1, "added" at anything else, and 3 is common), and clamping them made a client build a different gun list from the host's (found by the mod-sharing test).
- **What counts:** every add-on the game has imported, each identified by its Workshop ID (from its Steam install folder) or, for a local mod, its `modfile_*` folder. If the host has mods off, nobody's add-ons are used and nothing is compared.
- **Handshake:** the client sends its list in Hello (after the protocol version, which is checked first). With mods on, the host compares with its own; on any difference it sends the client what it's missing and what it has extra, then refuses the join.
- **The client's window:** lists the host's add-ons it's missing (marking any that aren't on the Workshop) and any it has that the host doesn't (to unsubscribe from, then restart, or ask the host to add), with **Subscribe to all** and **Cancel**. Cancel just closes it (the connection has already stopped). Subscribe subscribes to every missing Workshop item through Steam, starts each download with priority, turns mods on if they were off, shows progress, and when everything is installed says to restart Receiver and join again (a fresh launch imports them in the same title order as everyone else; an item installed mid-game would be imported last).
- **Gun order check:** after the welcome, the client applies the host's mod settings, rebuilds the open level's gun list the way the game does when a level loads (`GUISkinHolder.InsertGunMods`, which starts from the base list each time; the level built at launch may predate the imports), then compares it with the host's in order (shots, pickups and gear refer to guns by position) and leaves with a clear message if they differ. The host rebuilds its own list the same way when the session opens.
- **Logs:** hosting and joining log every add-on installed with its kind and Workshop ID, plus the mod settings.
- **Add-on guns are complete everywhere (0.5.4):** the game adds an add-on gun to the list as an empty placeholder and fills in its prefabs (`WeaponHolder.Load`, copying five references from the add-on, already in memory) only for the gun you carry. The shared item list (`PrefabRegistry`), the shot replay data (`GunCache`) and the ammo piles all come from that list, so each machine knew only its own add-on gun: the item list skipped the empty ones and its numbering differed per machine (another player's gun showed up as yours), and their shots replayed nothing (no trails, no holes). In a session every add-on gun is now filled in when a level loads (and before either list is built), and the shot data is rebuilt every run. Guns are named by their Workshop title (`Load` would otherwise rename them to the name inside the add-on), and a run's starting gun is taken by that name from the new level's list instead of the saved `selected_gun_index` setting.
- **Unsubscribe extras:** the add-on window also offers **Unsubscribe extras** for Workshop add-ons the host doesn't use (through Steam, with progress), then says to restart Receiver and join again.
- **Tested with two copies on one PC** (Direct IP on localhost, 11 Workshop guns, mods on, each player a different add-on gun): each holds their own gun and sees the other's, both item lists identical (77 entries, same hash), and a shot from each add-on gun is replayed on the other. Copies started outside Steam don't get Workshop items from Steam, so the test imports them from the Workshop folder the way the game does. Two copies on one PC also share the registry where the game keeps its settings, which is one more reason the starting gun is taken by name.

**Non-Workshop mods from the host (0.6.0, protocol 15):**
- **A local mod is its folder and its files:** a mod's path is its asset bundle file, inside the folder it loads from (`Mods/modfile_*`). A local mod is identified by that folder's name plus a SHA-256 hash of its files (top level only, like the game; each file's name, size and SHA-256, in name order; `Thumbs.db`, `desktop.ini` and dot-files don't count), so another version of the same mod is a difference too. Hashes are cached per folder while its file names, sizes and times are unchanged, and computed off the main thread before hosting or joining (part of "wait for add-ons": "checking your non-Workshop mods").
- **The host doesn't turn a mismatched player away:** it sends what differs (now with each local mod's hash, size and whether it can be sent) and keeps the connection open, outside the lobby (no player entry, no world traffic), while the player sorts it out. It answers pings, and drops the player after 10 minutes without a request (or an hour in all). At most 8 players at a time; more are refused as before.
  - **Bounded serving (0.7.0):** a piece is sent only while less than 1 MB to that player is still queued in the transport (LiteNetLib's reliable queue, Steam's P2P session state); later requests wait, at most ten of them, so a player who asks faster than they read can't pile data up in the host's memory. What one Steam account or address may fetch is capped at 4 GB for the whole session, across reconnects. Repeated Hellos while sorting out add-ons (each answered with the whole list of differences) count against the sender. Refusals sent to the player never carry the host's file paths; the details stay in the host's log.
- **Two windows on the joining player's screen**, side by side when both apply (the second where the game's dialogs sit, the first to its left, kept on screen):
  - **Workshop add-ons:** **Subscribe to all** (needs a restart before joining, as before), **Unsubscribe extras**, and new **Leave extras out for now**, which takes the host-less Workshop add-ons out of this game until it restarts without touching subscriptions.
  - **Other mods (not on the Workshop):** lists the host's mods you don't have (with sizes, or "already downloaded" / "in your Mods folder"), mods where the host has another version ("theirs is used instead of yours"), and yours the host doesn't have ("left out until you restart"). One button does all of it: **Download, leave out and join** (the label says what applies; "and join" only when the Workshop add-ons match).
  - Each window drops what's been fixed, and says when the other still has work. **Cancel** in either leaves. Closing them doesn't leave; the Multiplayer button brings them back while the host is waiting.
- **Fetching:** the player asks for one mod at a time by folder and hash; the host answers only for mods it reported missing to that player, from the folder it loaded them from, with the file list (names, sizes, SHA-256). The player checks the whole list first (plain names, no programs or scripts by extension, at most 64 files, 1 GB a file, 2 GB a mod, sizes and hash matching what the host announced), then asks for the files in 128 KB pieces, four ahead, at most 40 a second (under the host's rate limit), writing each into `<persistent data>/Multiplayer/Mods from hosts/incoming/` and checking every file's SHA-256 as it completes. A finished mod moves to `Mods from hosts/<first 16 hex of its hash>/<folder>/`. The host caps what one player can fetch at 8 GB per connection. A stall (30 s), a bad piece or a lost connection stops it with a message; finished mods are kept.
- **Applying (until restart, nothing in the Mods folder changes):** mods the host doesn't have are taken out of the game's loaded list and their asset bundles closed (`Unload(false)`: what's already in use stays), which also lets another version of the same bundle load. Then the host's copies load from the cache (or from the Mods folder, if a matching copy sits there unloaded) through the game's own importer, the gun list is rebuilt, and if nothing differs any more the player sends Hello again on the same connection. The next time, the cached copies load without downloading.
- **Load order:** the gun list and the level tiles come in the order mods were loaded, which differs between machines (local mods load at launch, Workshop items when Steam answers, fetched ones last). The Welcome now carries the host's add-ons in load order, and the joining game reorders its own to match before building the gun list.
- **Tested with two copies on one PC** (Direct IP, mods on): the host had two non-Workshop guns (loaded in the opposite order to the guest's); the guest had another version of one of them, an extra non-Workshop gun and an extra Workshop gun. The guest saw both windows, fetched 11.9 MB in 4.8 s, left its extras out, joined with the same five guns in the host's order, and played a run holding the host's gun while each saw the other's gun. A second launch of the guest found both mods in the cache, loaded them in 0.3 s and joined; the host sent nothing. The real Mods folder stayed empty throughout. Not tested: Steam P2P transfers, mods over 12 MB, tape and tile mods (same path as guns), and Workshop subscribe/unsubscribe (Steam isn't available to the test copies).

**Original plan:**

- **Host option:** an **Add-on sharing** checkbox on the host/multiplayer screen.
- **When on:** the host's active Workshop add-ons (guns, tiles) are listed to joiners, and the client auto-subscribes and downloads the missing items through Steam UGC before spawning. The game already tracks each mod's Workshop item ID, so the list is just that set of IDs.
- **Join gate:** the handshake compares the client's enabled mod list against the host's. A mismatch denies the join with a message naming the difference, so everyone runs identical content.
- **Why it matters:** the shared seed only reproduces the same tower if both sides have the same tiles and guns loaded, so the mod list and determinism are linked. It also keeps the weapon-choice dropdown identical for everyone.

## Distribution

- **Repo:** public on GitHub (`staltmedia/Receiver-Multiplayer`) from 0.7.0, with releases there.
- **What a release holds (0.7.0):** the drag-and-drop zip `ReceiverMultiplayer-<version>.zip`, built by `packaging/make-release.ps1` from an explicit file list (BepInEx's loader and core DLLs, the mod, LiteNetLib, the updater, the notices), and the updater on its own, `ReceiverMultiplayer-Updater.exe`, for players who'd rather not unzip anything. Windows only for now.
- **Updater (0.7.0, `src/Updater`):** one small window (.NET Framework 4.7.2 WinForms, nothing else to install). It finds the game beside itself (it lives in `BepInEx\plugins\ReceiverMultiplayer`) or in the Steam libraries (registry, `libraryfolders.vdf`, `appmanifest_234190.acf`), with a folder picker as the fallback, and installs into the Receiver folder by default. It reads the installed version from the DLL, asks GitHub for the latest release, and offers **Install X?** or **Update to X?** with OK and Cancel.
  - **Safe install:** the zip is downloaded into memory (never a temporary file) and checked against the SHA-256 digest GitHub publishes for the asset. Every entry must be one of the files a release ships, in its place (`winhttp.dll`, `doorstop_config.ini`, `BepInEx/core/*.dll`, `BepInEx/plugins/ReceiverMultiplayer/*`); anything else refuses the whole zip before a byte is written. It waits for the game to close, moves its own running file aside to replace itself, asks for admin rights only if the folder can't be written otherwise, and logs to `BepInEx\ReceiverMultiplayer-Updater.log`.
  - **Not signed:** a release is trusted as far as the GitHub account is. Signing with an offline key the updater checks would close that; it needs a key kept outside the repo.
- **In-game question (0.7.0):** at launch the mod asks GitHub for the latest release number (nothing about the player is sent). If it's newer: **Update to X?** with OK, Cancel and **Don't show again**, whichever way the mod was installed. OK starts the updater, which waits for the game to close, installs, and starts the game again (through Steam for a Steam copy); Cancel carries on with the version the player has. "Don't show again" sets `AskToUpdate = false` in `BepInEx\config\receiver.multiplayer.cfg`; from then on updating means running the updater, whose own checkbox turns the question back on.
- **Originally planned — smart installer:** a single installer that auto-detects the game. It reads the Steam install path (registry / libraryfolders.vdf) to find `steamapps/common/Receiver`, then installs BepInEx and the plugin. One window: **Install / Uninstall / Repair**. The user never hunts for a folder.
- **Secondary — Thunderstore:** a listing so r2modman / Gale install it in one click and manage BepInEx automatically. Receiver 2 already has a Thunderstore section; a Receiver 1 one is setup only.
- **Fallback — manual zip:** a drag-and-drop zip for people who won't run an .exe, and for Linux/Steam Deck (files work under Proton; the Windows installer does not run there). Label it “manual install.”
- **Workshop note:** Steam Workshop items download to `steamapps/workshop/content/<appid>/<itemid>/`, not the game folder, and Steam never executes them. Workshop can host add-on content and a listing, but the code mod itself is delivered by the installer or mod manager above, never by a Workshop subscription alone.

## Packaging hygiene

- **Strictly the mod files.** A shipped release contains only the mod's runtime files: the plugin DLL(s), any required asset bundle(s), and the installer (with its BepInEx payload). Nothing else.
- **No markdown or docs in the shipped mod.** This spec and any notes live only in the repo or outside it, never inside the distributed/zip build. Exclude README/CHANGELOG from the packaged artifact even when they exist in the repo.
- **One required exception — third-party notices:** LiteNetLib is MIT-licensed, and the MIT license requires its copyright and permission notice to accompany copies of the DLL. Ship a single plain-text `THIRD-PARTY-NOTICES.txt` beside the plugin with that notice; it is the only non-runtime file in a release.
- **Compact (0.7.0):** BepInEx's XML docs, changelog and version stamp are left out; the game root gets only `winhttp.dll` and `doorstop_config.ini`, and everything of the mod's own (the updater and the notices included) sits in `BepInEx\plugins\ReceiverMultiplayer`. The zip's timestamps are fixed, so the same inputs make the same zip.
- **No personally identifying or residual data** in any shipped or committed file: no author email, machine paths, session identifiers, generated attribution lines, or leftover scratch/log files. Strip build metadata where practical.
- **Separate source from output.** `.gitignore` the Unity/BepInEx build intermediates, local game-DLL references, and local config. The release workflow assembles the zip from an explicit allowlist of files, not “everything in the folder.”
- **Pre-release check:** unzip the release and confirm it holds only the files a player needs to run the mod.

## Build order

1. Plugin skeleton and Multiplayer menu button (BepInEx loads, button appears).
2. Transport abstraction, Steam lobby and Direct IP; waiting room with ready/unready, 3-second countdown and host Start Game (fade into a fresh seeded match); two players in the same seeded tower, late-join at the start spawn.

7. Synced world items (seeded piles, shared ammo pool, pickups, drops, ejected rounds and casings), carrying other guns' ammo, drop chooser, host modifiers.
8. Holster-hold gun cycling; using teammates' magazines. (Ammo and enemy multipliers dropped: not in the base game.)
9. Add-on sharing and the mod-list join gate.
